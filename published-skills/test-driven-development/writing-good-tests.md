# 写好测试

**何时加载本参考：** 写或改测试、添加 mock、为测试添加清理或辅助方法时。

## 概述

一个测试存在的意义，是抓住一种特定的“坏掉”。这里的一切由两条原则支配：

```
1. 每个测试都说得出它抓的是哪种坏
2. 每个测试都练的是真实的东西
```

严格的 TDD 会自然产出这两条：先写、并亲眼看着它对真实代码失败过的测试，已经证明了它能失败；只有当真实依赖确实太慢或在外部时，才配得上一个 mock。

## 原则一：说出它抓哪种坏

写测试主体之前，先回答：**哪种生产代码改动应该让这个测试失败——那个改动是 Bug 还是决定？** 一个测试靠抓住走错的分支、缺失的副作用、传错的参数、边界情况或被破坏的契约来挣得自己的位置。

**独立推导期望值。** 用字面量和手工核对过的 fixture；带字面 `want` 值的表驱动测试是首选形态。用被测代码（或它的辅助函数）算出来的期望值，无论代码做什么都会通过：

```typescript
// ❌ 镜像断言：两边由同一个构造函数计算——永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要变更探测器。** 如果只有“有意的决定”能让一个测试失败——某个常量的取值、报错文案的精确措辞、私有结构——它会在重构时炸响，在 Bug 面前沉睡。要测依赖那个决定的行为：不是 `expect(MAX_RETRIES).toBe(5)`，而是“失败的调用会重试 5 次，第 6 次永远不会发生”。

**测行为，不测文本。** 断言某个脚本、Skill 或配置里含有某一行原文，只能证明“源码等于源码”。应该拿受控输入运行脚本，断言输出、副作用或退出码。指导 Agent 的文档由消费它的 Agent 的行为来检验（superpowers:writing-skills）；写给人看的散文根本不配测试。

**测你的代码，不测框架。** 测你的代码在边界上做出的契约——你注册的路由、你发出的查询、你产出的载荷。上游机制是它们维护者该写的测试（经典反例：断言你的路由器会调用已注册的处理函数——那是框架的测试，不是你的）。当上游行为确实让你意外时，写一个狭窄的特征测试，点名那个假设。同样的边界也适用于你代码内部：构造函数、getter、常量和纯转发，只有在做校验、归一化、默认值、推导、约束或产生副作用时才配得上测试——否则去断言依赖它们的第一个消费者可见的结果。

### 闸门函数

```
写测试主体之前：
  说出哪种生产代码改动会让这个测试失败。

  说不出来              → 围绕一个可观察行为重新设计
  “源文本变了”          → 运行产物，断言它的效果
  只有有意的决定能让它失败 → 变更探测器；改测依赖该决定的行为

  确认期望值的推导没有用到被测代码。
  如果它复用了被测代码的逻辑或辅助函数：
    换成字面量或手工核对过的 fixture
```

## 原则二：练真实的东西

**mock 挣不到断言。** 对 mock 的断言，mock 在就通过、mock 不在就失败——它对组件本身什么也没说。要断言真实组件的行为；如果你检查的就是 mock 本身，要么去掉 mock，要么删掉这条断言。

```typescript
// ✅ 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 的存在性
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**用户的纠正：** “我们是在测一个 mock 的行为吗？”

**在正确的层级 mock。** 替换真实方法之前，先弄清它的每一个副作用；mock 掉慢的或外部的操作，保留测试所依赖的部分为真实。拿不准时，先对真实实现跑一遍测试，观察实际需要发生什么。

```typescript
// ❌ 这个 mock 吞掉了重复检测要读取的配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 慢的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**替身要具体。** 当参数、调用次数或顺序属于契约的一部分时，就断言它们——什么都接受的假对象什么也验证不了。给每个分支（成功、错误、格式损坏）配各自的 fixture 或 spy，让走错的分支无法满足期望。

**完整镜像真实数据。** 按现实中存在的完整结构 mock——所有文档里有的字段——而不只是你的测试读到的那几个。不完整的 mock 会静默失败：下游代码读到被省略的字段时，测试通过而集成坏掉。

**生产类只带生产方法。** 只有测试需要的清理逻辑放进测试工具，绝不作为 `destroy()` 挂在生产类上。自问：这个方法是不是只有测试调用？这个类是否拥有该资源的生命周期？答案不对 → 放测试工具。

**复杂 mock 不如真实组件。** 当 mock 的准备代码超过测试逻辑本身、mock 缺少真实组件有的方法、或 mock 一改测试就坏时，换成用真实组件的集成测试。**用户的提问：** “这里我们需要用 mock 吗？”

### 闸门函数

```
添加 mock 或测试辅助之前：
  列出真实方法的副作用；测试依赖的那些保持真实——
  在它们之下 mock 慢的/外部的层级。

  mock 响应完整镜像真实结构。

  只有测试调用的方法放进测试工具，不放生产代码。

  正要对 mock 本身做断言？
    去掉 mock，或删掉这条断言。
```

## 测试与实现一起交付

TDD 循环——失败的测试、最小实现、重构——就是“完成”的定义。交付该行为需要的测试，并且只交付这些：琐碎代码和写给人看的散文不配测试，为满足流程而写的测试则要永远付维护费。

## 变异检查

收尾之前，在脑中变异生产代码；每一种现实的变异都至少应有一个测试失败：

- 错误的常量或参数
- 走错的分支处理
- 缺失的状态变更或副作用
- 空返回或默认返回
- 对零、空、nil、未授权或格式损坏输入缺失校验

没有任何测试能抓住的变异，说明该行为无保护——或者测试是同义反复。

## 快速参考

| 当你…… | 做法 |
|--------|------|
| 写任何测试 | 说出它抓哪种坏——一个 Bug，不是一个决定 |
| 构造期望值 | 手工推导；绝不用被测代码算 |
| 测脚本或文档 | 运行它 / 压力测试它的消费者；绝不 grep 它的文本 |
| 想测依赖库 | 测你在边界上的契约，不测它文档里的机制 |
| 想断言被 mock 的元素 | 测真实组件，或去掉 mock |
| 正要 mock 一个方法 | 弄清它的副作用；在慢的/外部的层级 mock |
| 构造 mock 响应 | 完整镜像真实结构 |
| 需要只有测试用的清理 | 放进测试工具 |
| 看着 mock 准备代码膨胀 | 换成用真实组件的集成测试 |
| 写完一个测试文件 | 跑一遍变异检查 |

## 警告信号

- 准备和断言共享同一个对象，等式必然成立
- 测试只能通过 panic、崩溃或选择器缺失而失败
- 测试在每次有意改动时都失败，在意外破坏时从不失败
- 期望值藏在循环、构造器或辅助函数后面
- 测试在 grep 源文本，或断言某个被删除的符号保持被删除
- 就算只剩框架，这个测试也照样“有意义”
- 测试为覆盖率而存在，不检查任何副作用或结果
- 断言检查 `*-mock` 测试 ID，或者去掉 mock 它就失败
- 某个方法只被测试文件调用
- mock 准备超过测试的一半，或你说不清为什么需要这个 mock
- “保险起见”而 mock
