# 结构化设计表达

把复杂内容组织成低阅读成本、可逐层展开的图文结构。先建立全局坐标，再展开当前需要判断的部分；让图承担结构，让短文字承担目的、边界和反直觉信息。

## 开始前

1. 完整读取 [presentation-standard.md](references/presentation-standard.md)，遵守共同表达规范。
2. 根据任务类型只读取最接近的一个示例：
   - 系统架构、数据模型、Spec：读取 [engineering-system-example.md](references/engineering-system-example.md)。
   - 项目阶段、依赖与执行方案：读取 [project-plan-example.md](references/project-plan-example.md)。
   - 业务流程、角色交接与服务设计：读取 [business-process-example.md](references/business-process-example.md)。
   - 因果分析、方案权衡与复杂思路：读取 [complex-reasoning-example.md](references/complex-reasoning-example.md)。
3. 若任务横跨多个类型，先选决定理解主线的示例；只有确有必要时再读取第二个。

## 工作流程

### 1. 找到理解主线

先回答三个问题：

- 读者此刻最需要理解或决定什么？
- 困难主要来自结构、流程、状态、层级、依赖、边界还是取舍？
- 哪些内容属于主线，哪些只需让读者知道“存在”？

不要直接沿用用户最先列出的章节或维度。先从问题本身建立结构，再把用户已有观点放回结构中。

### 2. 建立语义模型

在画图前先明确：

- 核心对象及其职责；
- 对象之间的关系；
- 信息、任务或责任怎样流转；
- 生命周期和关键状态；
- 人工确认、停止点、系统边界；
- 已知事实、合理推断和尚缺信息。

不要让同一个状态图同时承载业务阶段、系统下一动作和资源占用状态。必要时拆成不同维度。

### 3. 渐进展开

按任务需要从以下层次中选择，不机械凑齐：

1. 一句话结论或目的；
2. 一屏极简全景图；
3. 核心结构图；
4. 主流程或角色交接图；
5. 关键状态、决策点或人工边界；
6. 核心约束、验收旅程或风险；
7. 实现映射和次级细节。

先给读者全局坐标，再进入当前讨论的局部。讨论某个模块时，优先复用总图并用颜色突出当前位置，不另画一套语义不一致的全景图。

### 4. 控制详略

- 核心对象：显示名称、关键字段或步骤、中文职责说明。
- 次级对象：降低颜色强度，只显示名称或一句职责。
- 实现细节：放在后续小节、折叠说明或映射表，不挤占总览。
- 工程类图：类名和字段名保留英文，职责注释使用中文。
- 结构顺序优先于视觉对称；按聚合、总分和流转关系布局。

### 5. 用短文字补图的边界

每张图后通常只写 1–3 句，优先说明：

- 为什么这样切分；
- 图上无法表达的约束；
- 反直觉点或容易混淆的概念；
- 尚未确定或需要用户决定的地方。

不要把节点和箭头再复述一遍。删除图后仍有独立信息量的文字才值得保留。

## 对话与正式文档

- 对话：只展示当前决策切片，通常是一张主图和少量补充文字。
- Spec 或正式方案：保持相同实体、关系、状态和边界，再补异常、约束、验收旅程和实现映射。
- 不要在正式文档中静默增加对话中未出现的新语义；需要新增时明确指出。

## 输出前自检

- 是否先给了全局坐标，再展开局部？
- 图是否真正降低理解成本，而非把文字换成方框？
- 核心和次级内容是否有明显详略？
- 名称、关系、状态在各图和文字中是否一致？
- 状态名称是否说明对象和业务目的，避免 `processing`、`collecting` 等宽泛词？
- 颜色是否承载稳定语义，并在正文中解释？
- 简单内容是否被强行复杂化？
- 用户要求的关键问题是否已得到直接回答？

若图没有明显提升理解，改用短列表、表格或简短文字，不为了调用本 Skill 强行画图。
