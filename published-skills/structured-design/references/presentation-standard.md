## 1. 核心原则

采用“结构优先、渐进展开、图为主线、短文字补边界”的表达方式。

- 图承担：组成、关系、顺序、状态、层级、依赖和边界。
- 文字承担：目的、理由、约束、反直觉点、争议和未决信息。
- 总览承担：建立全局坐标，不承载全部字段和异常。
- 细化图承担：解释当前模块，不重新发明全局语义。

不要把“图文并茂”理解成每段都必须有图。图只有在能降低理解成本时才出现。

## 2. 渐进式信息层级

根据任务复杂度选取层次，不要求每次全部出现：

```text
结论 / 目的
→ 一屏极简全景
→ 核心结构
→ 主流程
→ 关键状态或决策边界
→ 核心约束、风险与验收旅程
→ 实现映射和次级细节
```

### 一屏极简全景

- 控制在读者能一次看完的范围内。
- 一般突出 3–7 个核心概念；次级概念可只显示名称。
- 让读者先知道“现在在哪里、最终到哪里、主要经过什么”。
- 不在总览中展开完整字段、全部异常和数据库映射。

### 核心结构

- 展示实体、模块、角色或决策因素。
- 使用总分、聚合和依赖顺序组织。
- 核心对象完整，次级对象降级，不平均用力。

### 流程与状态

- 流程图说明动作和交付怎样发生。
- 状态图说明同一对象的生命周期。
- 角色、系统或边界不同时，用分区表达交接。
- 人工确认门和系统停止点必须可见。

## 3. 图形选择

| 主要问题 | 首选表达 |
|---|---|
| 有哪些核心对象、字段和关系 | Mermaid `classDiagram`；需要严格基数时使用 ER 图 |
| 信息、任务或责任怎样流转 | `flowchart TD` 或 `flowchart LR` |
| 多角色或多系统怎样交接 | 带 `subgraph` 分区的流程图 |
| 一个对象怎样经历生命周期 | `stateDiagram-v2` |
| 模块位于总体方案哪一段 | 复用总览图并高亮当前范围 |
| 多个方案怎样比较 | Markdown 表格，必要时加决策路径图 |
| 因果与二阶影响 | 因果关系图或影响链 |
| 文件、组织或概念层级 | 文本树；关系复杂时再用图 |
| 字段与数据库表映射 | 次级映射表，不抢占业务主图 |

表格、目录树、YAML 和代码样例本身已经具有结构，不要强行转成 Mermaid。

## 4. 详略与布局

### 三层信息密度

1. **核心层**：完整显示关键字段、步骤和中文职责。
2. **支撑层**：显示名称和一句职责，使用较淡颜色。
3. **实现层**：数据库表、接口和技术映射放在次级文字或附录。

### 布局规则

- 逻辑结构优先于视觉对称。
- 同一聚合的内容放在一起；先总后分，再按主要流转顺序排列。
- 不为了让线更短而打破父子、聚合或阶段关系。
- 线过多时，先检查是否混入了不同维度；必要时拆图，而不是继续缩小字体。
- 允许局部从左到右、整体从上到下，或者相反；关键是顺序有语义。

## 5. 语言与注释

### 工程类图

- 类名和字段名使用英文，例如 `SalesTask`、`status`、`sourceRowIds`。
- 中文说明放在类卡片底部或图后，说明对象承担什么职责。
- 简单类用一句话；复杂聚合说明它冻结什么、承接什么、向哪里交付。
- 不必额外重复“类名”二字。

### 非工程图

- 默认使用中文节点名称。
- 已经稳定使用的英文术语可以保留，并在首次出现时补中文解释。
- 状态名必须包含对象或目的，例如“等待确认公司候选”，不要只写“等待评审”。

## 6. 颜色语义

同一份内容中保持一致：

| 颜色 | 建议样式 | 语义 |
|---|---|---|
| 蓝色 | `fill:#e8f1ff,stroke:#7b9acc` | 当前系统、执行主线、正在讨论的范围 |
| 紫色 | `fill:#f1e8ff,stroke:#9b7bc4` | 分析、模型判断、方案选择 |
| 黄色 | `fill:#fff4d6,stroke:#d9a441` | 输入、中间材料、待判断信息 |
| 绿色 | `fill:#e6f5e6,stroke:#7aa67a` | 已确认事实、稳定结果、成功交付 |
| 橙色 | `fill:#ffe9c7,stroke:#d98b3a,stroke-width:3px` | 人工确认门、暂停点、硬边界 |
| 红色 | `fill:#fde8e8,stroke:#c56f6f` | 确定性错误、终止、不可接受风险 |
| 灰色 | `fill:#f2f3f5,stroke:#a5a8ad` | 次级、未来、当前范围外 |

用了颜色，就用一句话点明关键差异。颜色是语义，不是装饰。

## 7. 图后文字

每张图后通常保留 1–3 句，只写图上看不出来的内容：

- 为什么这样切分；
- 哪个边界不可跨越；
- 什么情况会暂停、失败或需要人工决定；
- 哪些地方仍是推断或尚缺信息。

自检：删掉图后，这段文字是否仍包含独立信息？如果没有，就是在复述图。

## 8. 核心不变量与验收场景

### 核心不变量

不要直接堆成密集条款。先用 3–5 个“护栏卡片”表达最重要的不可破坏规则：

```text
[对象边界] 一个处理单元冻结什么
[顺序边界] 哪一步未完成时不能前进
[数据边界] 什么必须保留，什么不得静默覆盖
[人工边界] 哪些结果必须停下来确认
[交付边界] 完成究竟交付什么对象
```

完整约束清单可以放在后续表格中。

### 核心验收场景

优先写 3–5 条端到端业务旅程，而不是先列大量局部检查项：

```text
给定起始条件
→ 发生关键动作
→ 跨越主要边界
→ 得到可观察结果
```

每条旅程应让读者看出“系统为什么算完成”。详尽测试矩阵放在实现或测试章节。

## 9. 对话与正式文档一致性

- 对话和 Spec 使用同一套实体名、关系、状态和边界。
- 对话只展开当前需要决定的切片，不等于降低语义精度。
- Spec 增加异常、约束、验收和实现映射，但不静默改变对话结论。
- 讨论局部时复用总图并高亮当前范围，让读者始终知道它位于全局哪里。
- 如果新证据改变了总图，明确指出变更位置和原因。

## 10. Mermaid 实操

- 节点标签一律使用双引号：`A["文本"]`。
- 中文括号、斜杠、冒号、问号等放在引号内。
- 换行使用 `<br/>`，不要使用 `\n`。
- `subgraph` 内使用 `direction TB` 或 `direction LR` 控制顺序。
- `style` 或 `classDef` 统一放在图的末尾。
- `stateDiagram-v2` 的状态标识符不要包含空格；用别名显示中文。
- 避免 `A & B --> C` 等老渲染器可能不支持的合并写法。
- 复杂图优先拆分，不依赖缩小字体解决信息过载。

## 11. 常见失败方式

| 失败方式 | 实际后果 | 修正方式 |
|---|---|---|
| 把整套系统塞进一张图 | 线多、字小、读者失去主线 | 先极简总览，再按模块展开 |
| 为了布局漂亮打破聚合关系 | 图好看但语义顺序错误 | 先按总分、聚合和流转布局 |
| 所有类都显示完整字段 | 核心与次级没有层级 | 次级类只显示名称或一句职责 |
| 状态使用 `serving`、`collecting` | 看不出对象和业务目的 | 写成“获取公司及联系人事实”等具体状态 |
| 一个状态图混入多种维度 | 生命周期、下一动作和资源占用互相冲突 | 拆成业务阶段、控制动作和资源状态 |
| 图后大段复述节点 | 阅读成本没有下降 | 只补目的、边界和反直觉信息 |
| 每个局部重新画一套总图 | 实体名称和流程逐渐漂移 | 复用总图并高亮当前部分 |
| 简单问题也套完整模板 | 形式成本高于理解收益 | 改用短文字、列表或表格 |
