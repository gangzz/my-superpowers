六个场景

1 有人拿到链接但没有密钥来访问 页面、文件、WebSocket 一律拒绝；密钥首次使用后从地址栏消失，换成 HttpOnly cookie 20 例
无凭访问——不带密钥或密钥错误页面、文件、WebSocket 一律 403 或拒绝；错密钥不能靠有效 cookie 洗白6
防泄漏——密钥通过验证后地址栏密钥被抹掉，换发 HttpOnly SameSite=Strict cookie；响应带防泄漏、防嵌入头6
跨源——其它网站的页面带 cookie 连接同源放行，跨源拒绝2
正常路径——正牌访客后续访问凭 cookie 一路可用；恶意空载荷不崩服务器6

3 客户端发来畸形、残缺或超大的消息，或多个连接同时进来 不崩溃、不乱记录、不为超大帧提前分配内存 48 例
编解码——消息尺寸从 0 到 65536+ 字节（含四个边界值）手写的 WebSocket 帧编解码全部正确，JSON 往返无损27
恶意输入——残缺帧、未掩码帧、超大帧残缺的等待补齐、违规的拒收、超大的在分配内存前拒绝5
事件流转——你在页面上点了选择写入 state/events 供 Agent 读取；非选择事件不写；新屏幕清空旧事件6
并发与热更新——多客户端 / 文件被修改并发正常、死连接被清理、html 变更自动推送刷新、畸形 JSON 不崩10

用例最多的原因：零依赖政策下他们手写了 WebSocket 协议实现。手写协议，边界枚举就是必需品——哪天换成现成库，编解码一组可以整体退休。
