# 测试地图

## 概述

把测试套件整理成"场景 → 情形 → 案例"三层的单文件 HTML 报告，让人只读测试名就能理解测试保护什么，逐层下钻，不必读测试代码。

**核心原则：**

- 只提取测试名，不读测试实现。中文"测试点"是测试名的直译；名字与实现不符属于测试缺陷，应打回重命名，不在本 Skill 内修正。
- 报告只呈现事实（场景、情形、案例、计数），不写观点和评价。"测试是否过多"这类判断放对话里说。
- 阅读单位逐层放大：场景（3–8 个）→ 情形（每场景 2–5 行）→ 案例（全部）。读者停在哪层由他的问题决定。

## 调用前提

两种模式，规则不同：

- **首次建图**：成本高（全量扫描、聚类、名实抽查），仅在用户显式调用，或 Agent 说明理由且用户明确同意后进行。
- **增量更新**：项目已存在 `test-map.json` 时，本 Skill 获准自动调用——本次会话新增、修改或删除了测试后即触发增量更新，不必再次询问；完成后必须向用户汇报增量。
- **排除**：本次未改动任何测试；项目没有测试（如实说明，不生成空报告）；用户说过不要自动更新。
- **回退**：自动模式只改 `test-map.json` 和 `test-map.html` 两个文件，可用 git 直接回滚；用户随时可要求停用自动更新，改回手工调用。

## 工作流

### 1. 提取测试名

只用文本搜索，不读测试体：

- JS/TS：`grep -E "^\s*(test|it)\(" `，注意自定义 runner（如 `await test('...'`）需先看一个文件确认模式。
- Python：`grep -E "def test_|class Test"`。
- Go：`grep -E "^func Test"`。
- Shell 等无具名用例的脚本：取文件头注释和文件名，作为文件级条目。

同时记录：每个文件的用例数、总数。后续每层计数必须与这里对得上。

### 2. 聚类

- **场景**：3–8 个，场景化描述——"当 X 发生时"加"测试保证的结果"。X 是使用者或攻击者的真实处境（"有人拿到链接但没有密钥来访问"），不是技术模块名，不用比喻。
- **情形**：每个场景内 2–5 行，各带 2–6 字短标签（如"无凭访问""端口回退"），说明具体情形和保证结果。
- **案例**：每条测试逐一归属某个情形，写一句中文测试点（测试名直译，不加内容）。
- 若测试分布对应一条主流程，补 flow 流程条定位场景位置；安全边界节点用 `gate` 标记。
- 计数自下而上核对：案例数之和 = 情形计数之和 = 场景计数 = 提取阶段的总数。对不上就回去修聚类，不得凑数。

### 3. 名实抽查（首次建图必做）

测试点由测试名直译而来，名字可能说谎。首次建图时每个场景抽 1–2 条（合计不少于用例总数的 5%），读其测试实现，核对断言与名字是否相符：

- 相符：在交付时报告抽查数量与结果。
- 不符：该条在报告 `point` 末尾标注"（存疑：断言与名字不符）"，并在交付时单独列出——这是测试缺陷，应打回重命名，不由本 Skill 修正。

抽查是本 Skill 唯一允许读测试实现的环节。自己用 TDD 流程写出的测试不在抽查范围（Verify RED 已保证名实相符）。

### 4. 生成 test-map.json

结构（最小示例）：

```json
{
  "title": "示例项目 测试地图",
  "lede": "一句话说明报告对象和读法。",
  "meta": ["42 个具名用例", "commit abc1234", "由 grep 测试名生成，未读实现"],
  "anchor": { "commit": "abc1234", "generatedAt": "2026-08-19T14:00:00+0800" },
  "flow": [
    { "label": "认证门", "sub": "场景 1 · 20 例", "kind": "gate" },
    { "label": "文件服务", "sub": "场景 2 · 17 例", "kind": "main" },
    { "label": "遥测边界", "sub": "场景 3 · 5 例", "kind": "aside" }
  ],
  "flowNote": "琥珀色是安全门——测得最重的位置。",
  "scenes": [
    {
      "num": "1",
      "title": "有人拿到链接但没有密钥来访问",
      "outcome": "页面、文件、连接一律拒绝",
      "count": "20 例",
      "gated": true,
      "clauses": [
        { "label": "无凭访问", "situation": "不带密钥或密钥错误", "result": "一律 403", "count": 6 }
      ],
      "note": "可选：该场景的图外说明（如用例密集的原因）。",
      "caseGroups": [
        {
          "file": "auth.test.js",
          "cases": [
            { "name": "GET / without key is rejected with 403", "point": "无密钥访问首页返回 403", "clause": "无凭访问" }
          ]
        }
      ]
    }
  ],
  "footer": "来源与生成方式说明"
}
```

说明：`kind` 取 `main`/`gate`/`aside`；`gated: true` 给安全场景卡上色；跨多个文件的场景在 `caseGroups` 里分组，模板会渲染文件分组行；`flow`、`flowNote`、`note` 可省略。`anchor` 是增量更新的锚点（模板不渲染它）：记录本次生成时的 git commit 与时间，供下次定位变更范围。

### 5. 注入模板生成单文件

模板是本 Skill 自带的 `template.html`，固定不改。注入命令（在目标项目目录执行，`$SKILL_DIR` 为本 Skill 目录）：

```bash
node -e '
const fs = require("fs");
const t = fs.readFileSync(process.argv[1], "utf8");
const d = fs.readFileSync("test-map.json", "utf8");
fs.writeFileSync("test-map.html",
  t.replace("window.DATA = null; /*__TESTMAP_DATA__*/", "window.DATA = " + d + ";"));
' "$SKILL_DIR/template.html"
```

产物 `test-map.html` 自包含、无外部依赖，双击即可打开。需要数据热更新时，也可把 `template.html` 和 `test-map.json` 放同一目录，起本地服务（`python3 -m http.server`）访问模板，它会自动 fetch 数据。

### 6. 验证与交付

- 用 `node -e 'JSON.parse(...)'` 确认 JSON 合法；确认注入后的 HTML 包含数据（grep 一个测试名）。
- 交付时报告：总数、场景数、放置路径、名实抽查结果（抽了几条、几条相符、存疑清单），以及无法归类或名字含糊的测试清单（如实列出，不硬塞进场景）。

## 增量更新（自动模式）

已有地图时不重建，也不全量扫描：

1. **定位变更**：本次会话自己改过的测试文件是已知信息，直接用；跨会话用 `git diff --name-only <anchor.commit>` 过滤测试文件。没有 git 的项目退回全量重新提取——grep 本身成本很低，增量性保留在下一步（只归类差集），不用 mtime 这类不可靠信号。
2. **只对变更文件重新提取测试名**，与 JSON 中已记录的案例求差集：新增、删除、改名。
3. **归类**：新增案例归入已有场景/情形，必要时新增一行情形；出现无法归入任何场景的全新主题时，向用户提议新场景，不擅自扩。删除的案例移除，改名的更新测试点。不推翻已有聚类（防止地图漂移），除非用户要求重建。
4. **更新**各层计数和 `anchor`，重新注入生成 HTML。
5. **汇报增量**：新增/删除/改名各几条、归入了哪些情形、有没有待用户决定的新场景提议。不重述全图。

## 不要做

- 不读测试实现来"改进"测试点描述。
- 不在报告里加观点、评分、建议。
- 不为凑场景数量拆分或合并语义不同的测试组。
- 不用比喻代替场景描述。
