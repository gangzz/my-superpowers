# test-map：初始设计

## 背景

原创 Skill，无上游来源。起因：用户的核心诉求是低成本理解 Agent 写出的大量测试——"测试也要给人服务，首先要让人好阅读、知道测试了什么，从而才能参与进来"。

设计经过一轮真实试验迭代：以 `upstream/superpowers/tests/`（142 个具名用例 + 28 个 Shell 脚本）为对象，从平铺清单逐步收敛到最终形态。用户逐项确认的结论：

- **场景优先**：顶层是"当 X 发生时 → 测试保证的结果"的场景卡（用户："承诺书就是场景，告诉我价值在哪里，我一下就知道了"）。
- **三层折叠**：场景 → 情形 → 逐条案例，明细默认折叠（用户："让我看到总体，然后再看细节"）。
- **案例层必须有中文**：三列表格——案例（含所属文件）、测试点、情形。
- **场景化描述，不用比喻**：用户明确否决了拟人/比喻腔（"人话不是这么说的，我收回"），要求真实情形加系统行为。
- **报告不夹观点**："测试是不是太多"这类分析被用户删除——HTML 定位是纯报告。
- **本地单文件**：用户否决远程 Artifact，要求本地可直接打开；采纳用户提出的 JSON + 固定 HTML 模板方案，注入生成单文件，必要时起本地服务。
- **否决"缺口视图"**：用户担心"只看缺口不看守卫"会诱导为填格子造垃圾用例，与"为覆盖率写测试"同病。故 Skill 不提供缺口分析视图；缺口问题留给用户主动提问。

## 关键设计决定

- **只读测试名，不读实现**。这是低成本的来源，也是诚实边界：测试点是名字直译，名字说谎属于测试缺陷，打回重命名而不是替它圆场。
- **计数逐层核对**：案例 = 情形之和 = 场景计数 = 提取总数，防止聚类时静默丢用例。
- **模板固定、数据驱动**：`template.html` 随 Skill 分发，渲染用 textContent（数据不作为 HTML 解析）；双模式——注入 `window.DATA` 出单文件（默认），或同目录 fetch `test-map.json`（起 serve 时）。
- **增量更新**：地图建一次，之后只归入新增用例、汇报变化，避免重复的全量阅读。

## 与 test-driven-development 的关系

分成两个 Skill（用户确认）：TDD 管"怎么写测试"（实现前触发），test-map 管"怎么读和汇报测试"（写完后或接手陌生项目时触发），且 test-map 可脱离 TDD 独立使用（首次试验对象就是别人的测试）。TDD 的 SKILL.md 只加"面向人的交付"一节引用本 Skill，不复制内容，保持其与上游可对比。

## 调用方式

- 仅手工调用。
- `agents/openai.yaml` 设置 `allow_implicit_invocation: false`。
- Agent 主动建议时必须说明具体问题、预期收益和主要成本，并等待用户决定。

## 验收

### 应使用

1. 用户显式调用，且需要向人交付测试全貌，或需要读懂一个陌生项目的测试套件。
2. 已有地图的项目新增测试后，用户要求更新。

### 不应使用

1. 项目没有测试。
2. 用户只问单个测试的问题（直接回答即可，不必建图）。
3. 用户未显式调用，且 Agent 无法说明具体问题与成本收益。
