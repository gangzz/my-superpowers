# Brainstorming 个人工作流决策

## 背景

上游 Superpowers 的 brainstorming 强调自动介入、完整设计流程和强制落盘。这能降低遗漏设计风险，但会让简单开发持续发散、延迟实施。本仓库只供个人使用，目标是选择性维护和安装单个 Skill，并持续跟随上游 Git 更新。

## 决策

- Skill 名称继续使用 `brainstorming`，正文使用简体中文。
- brainstorming 不得自行进入完整流程：用户显式调用时直接进入；否则只能说明介入理由并询问，获得用户明确同意后才能开始。
- 每条消息围绕一个决策主题提出 1～3 个相关问题；后一个问题依赖前一个答案时，每次只问一个。
- 关键假设、角色、子系统、冲突约束或高成本不可逆决策较多时，先综合复述当前理解并请用户确认。
- 只在存在实质不同的路径时比较 2～3 个方案；简单、明确、可逆的问题直接给出推荐方案。
- 用户选定方案后以其为当前基线；发现可能显著改善结果的新方案时，必须先询问用户是否重新打开比较。
- 默认用 Markdown、表格、文本树和 Mermaid 表达设计。Visual Companion 仅在用户主动要求，或静态 Markdown 无法有效表达复杂交互和动态状态时考虑；后一种情况也必须先获得用户许可。
- 完整设计获得批准后，写入简洁的决策记录，再进入后续计划阶段。

## 决策记录约定

个人 Skill 的定制决策统一放在：

```text
my-skills/decisions/<skill-name>/YYYY-MM-DD-<topic>.md
```

对应 Skill 名称先作为目录，日期放在文件名开头。不同 Skill 因此拥有独立的决策记录和定制依据。

写入记录后不自动执行 Git commit；只有用户明确要求时才提交。

## 边界与约束

- 上游原始 Skill 保留在独立仓库 `upstream/superpowers/skills/`，个人版本保留在 `my-skills/`。
- 不把个人定制提交给上游 Superpowers。
- 不以安装整个 Plugin 为前提；后续按需把单个 Skill 加入 Codex 或 Claude Code。
- 上游更新后，以本目录中的决策记录作为复核个人改动的依据，不机械覆盖本地版本。

## 验收标准

- 未经用户显式调用或二次许可，不进入完整 brainstorming 流程。
- 简单任务不会被强制扩展成多方案、逐段审批和交互式演示。
- 复杂设计仍能澄清关键假设、确认关键边界并形成可追踪记录。
- 每个个人 Skill 的定制决策都能在自己的 `my-skills/decisions/<skill-name>/` 目录中找到。
