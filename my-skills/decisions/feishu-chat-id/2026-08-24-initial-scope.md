# feishu-chat-id：初始范围与实现决策

## 目标

创建一个显式调用的原创个人 Skill，一次性取得用户当前指定的飞书群 `chat_id`，输出可复制进业务项目 `.env` 的配置行。Skill 本身不修改业务项目、不保存绑定、不发送群消息，也不承担持续监听。

## 已知事实

- 飞书官方 Node SDK 支持 `WSClient` 长连接与 `EventDispatcher`，可订阅 `im.message.receive_v1`，无需公网回调地址。
- 消息事件的 `message.chat_id` 是来源会话 ID；群消息可通过 `message.chat_type === "group"` 判断。
- 只接收用户在群内 `@机器人` 的消息可使用只读权限 `im:message.group_at_msg:readonly`；本 Skill 不需要发送消息或读取全部群消息的权限。
- 飞书也提供“获取用户或机器人所在群列表”API，但返回群列表；仅按名称无法排除同名群误选。
- 长连接事件是集群投递：同一应用并发运行多个长连接客户端时，事件只会投递给其中一个客户端，而不是广播给全部客户端。
- 本仓库发布时复制 Skill 运行文件，安装时把发布目录链接到用户 Skill 目录；不会自动为单个 Skill 安装 npm 依赖。

## 方案比较与决定

### 群 ID 取得方式

采用“长连接 + 本次随机确认码 + 用户在目标群内 `@机器人`”方案，不采用列群或按群名搜索：

- 用户的操作发生在目标群本身，随机码把事件与当前运行绑定，能避免同名群误选。
- 只读取当前运行所需的一条群消息，不枚举机器人所在的全部群。
- 不需要 Webhook、公网域名、数据库或业务绑定状态。
- 成功或超时后立即关闭连接。

只接受长连接就绪后收到的群文本事件，要求 `message.mentions` 非空且文本包含本次随机码。结合最小权限 `im:message.group_at_msg:readonly`，事件必须由用户在目标群真正 `@机器人` 触发；随机码再把它与当前运行绑定。虽然随机码本身已经使历史消息碰撞概率极低，仍通过“就绪后才开始接受”明确限定当前运行窗口。

### 凭证输入

采用每次交互输入，不要求用户在本仓库或业务项目中配置 `.env`：

- App ID 可见输入；App Secret 隐藏回显。
- 不接受凭证命令行参数，避免进入 shell history 和进程列表。
- 不读取环境变量或现有 `.env`，避免 Skill 与业务项目配置耦合。
- SDK 依赖在询问凭证前准备，npm 子进程不会接触本次输入的凭证；同时显式移除继承环境中的常见飞书凭证字段。

判断：对于低频、一次性取群 ID 的任务，交互输入比要求每个项目预先配置凭证更轻，也更符合“不保存凭证”的边界。代价是每次运行都要重新输入，且必须有真正的交互式终端。

### SDK 依赖

固定使用官方 `@larksuiteoapi/node-sdk@1.73.0`：

1. 若 Skill 自身可解析到完全相同版本，则直接使用。
2. 否则安装到系统随机临时目录；npm cache 也指向该目录。
3. 使用 `--ignore-scripts --no-audit --no-fund`，运行结束删除整个临时目录。
4. 不引用 `/Volumes/DataExt/projects/overseas/node_modules`，不复制整个 SDK，不修改仓库根 `package.json`。

这样符合当前发布/安装机制，也避免把依赖写进开发或发布目录。主要成本是首次或无本地同版本依赖时需要访问 npm，启动会更慢。

## 明确不迁移的旧业务行为

- `发送到此群` 的持久绑定语义；
- SQLite `Setting` 与 `feishu_notification_chat_id`；
- 群内确认回复、日报或业务通知发送；
- Outreach、邮件回复通知和 workspace 初始化；
- 读取或修改业务项目 `.env`。

## 风险与回退

- 成功、超时和连接错误都调用 `WSClient.close({ force: true })`；CLI 退出会释放其余进程句柄。
- SDK 日志被静默，错误只输出经过约束的中文提示，不打印错误对象或堆栈。
- 进程被 `SIGKILL` 时无法执行清理，这是操作系统级不可恢复中断；正常退出、超时和普通信号退出会清理临时目录。
- 不做在线飞书验证时，只能确认结构、过滤、超时关闭和依赖准备；真实权限、应用后台配置和事件投递仍需一次人工实测。

## 最值得关注的三个盲点

1. 同一 App ID 是否已经有其他长连接消费者；若有，本次可能收不到事件。
2. 应用是否已真正发布机器人能力、事件订阅和群内 `@机器人` 消息权限，而不只是后台草稿配置。
3. 运行环境是否允许访问 npm 与飞书开放平台；临时依赖方案不会借用旧项目，但增加一次外部下载。

## 可能改变结论的关键问题

- 如果未来飞书提供能由用户在目标群内直接生成、且可验证唯一性的官方取 ID 入口，可用它替代长连接并进一步减少权限与依赖。
- 如果此操作从低频一次性变成高频批量任务，临时安装 SDK 和每次输入凭证的机会成本会上升，应另行设计安装依赖或受控凭证方案；不能在本 Skill 内悄悄扩展。

## V2 TODO：凭证与权限预检

MVP 不增加权限探测，先以最小长连接取值流程完成首次发布和真实群测试。V2 再调研并实现可确定检测的预检项：

- 在不保存凭证、不打印 token 或鉴权信息的前提下，验证 App ID / App Secret 是否有效；
- 调研官方 API 能否可靠确认机器人能力、长连接订阅方式、`im.message.receive_v1` 事件订阅、`im:message.group_at_msg:readonly` 权限及其已发布状态；
- 把“API 可确定检测”和“只能由用户去开发者后台确认”分开，不把推测包装成检测成功；
- 权限不足时输出最小、可操作的缺项提示，不自动申请权限、不扩大到发送消息或读取全部群消息；
- 预检结束后仍不得保存 App Secret、tenant token、鉴权头或 chat_id。

如果官方 API 无法验证某一配置，V2 应明确说明不可检测并给出人工检查入口，不能为了实现“全自动探测”引入更高权限。

## 当前判断

当前方案在“精确目标群、无需公网回调、不保存凭证与绑定、低频一次性运行”之间平衡最好。对本地确定性行为信心高；对真实飞书后台配置与在线投递，在完成一次端到端实测前信心中等。
