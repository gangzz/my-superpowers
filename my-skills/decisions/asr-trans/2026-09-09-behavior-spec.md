# asr-trans 行为 Spec

## 1. 文档职责与状态

本文定义 `asr-trans` 的产品边界、行为契约和验收标准，供后续评审、实现调整和发布判断使用。

- `my-skills/asr-trans/SKILL.md`：Agent 实际调用时读取的运行指令。
- `my-skills/asr-trans/references/output-schema.md`：内部纠错清单与最终 JSON 的详细格式契约。
- `my-skills/asr-trans/scripts/`：确定性抽取、合成、校验与离线测试。
- 本文：解释为什么这样设计、什么结果才算正确，以及当前还有哪些事实未被验证。

本文描述的是开发版预期行为，不代表已经完成发布、安装或真实媒体端到端验证。

## 2. 问题与目标

### 问题

普通 ASR 可以生成文本和时间戳，但直接把整份结果交给大模型重写，容易造成漏句、越权润色、时间漂移或 JSON 结构损坏。另一方面，只保留未经纠错的 ASR 原文，又难以可靠处理专有名词、英文缩写、数字和同音词。

### 目标

输入一个本地中文音频或视频文件，输出一份经过语义纠错且保留原始声学时间依据的 JSON，供字幕、检索或后续剪辑使用。

成功结果必须同时满足：

1. 语义层只纠正确有依据的识别错误，不改变实际说话内容。
2. 时间层只使用 ASR 返回的真实边界，不按字符插值或伪造时间。
3. 结构层由确定性脚本合成和校验，全文与对齐单元可机械证明一致。
4. 权限层不静默覆盖既有输出，也不把依赖下载或外部写入视作默认授权。

## 3. 用户与使用场景

主要用户是需要把本地中文口播材料继续用于字幕、检索或剪辑的 Agent 使用者。

典型调用：

```text
$asr-trans <media-path>
  [--alignment sentence|token]
  [--output <json-path>]
  [--force]
```

- 默认生成句子级对齐，适合阅读、检索和普通字幕。
- 用户明确选择 `token` 时生成更细粒度对齐，适合后续精细定位。
- 默认输出到源文件同目录的 `<stem>.transcript.json`。
- 输出已存在时停止；只有显式 `--force` 才能替换。

## 4. 范围

### 第一版包含

- 本机已有且 FFmpeg 可读取的音频或视频。
- 以中文口播为主、允许夹杂英文缩写和数字的内容。
- `sentence` 与 `token` 两种对齐模式。
- 使用 FunASR 的 ASR、VAD 和标点模型生成原始文本及时间边界。
- 由当前执行 Skill 的大模型生成稀疏纠错清单。
- 通过确定性脚本合成、原子写入并再次校验最终 JSON。

### 第一版不包含

- 口语清理、去语气词、删除重复、修正说错重来或文案润色。
- 翻译、多语言自动识别、说话人分离、强制对齐或剪辑决策。
- 在脚本中调用外部大模型 API。
- 人工确认级准确率承诺。
- 字符级时间承诺；`token` 是声学 token 或必要的连续 token 组。
- 在最终文件中保留 ASR 原文、原 token 或纠错审计记录。

## 5. 系统边界与数据流

```text
本地媒体
  -> FFmpeg 转为临时 16 kHz 单声道 WAV
  -> FunASR 生成全文、句子与 token 时间
  -> extract_asr.py 做完整性和时间线检查
  -> 临时 raw.json
  -> 当前 Agent 只生成稀疏 corrections.json
  -> transcript_json.py 合成终稿
  -> transcript_json.py 独立校验
  -> 最终 transcript.json
```

`raw.json` 和 `corrections.json` 只存在于本次运行的临时目录。成功或失败后都应清理临时目录。最终输出只保留纠正后的文本、来源文件名、媒体时长和对齐单元。

## 6. 核心行为契约

### 6.1 输入与依赖

- 输入必须解析为存在且可读的普通文件。
- `ffmpeg`、`ffprobe` 必须可用。
- 优先使用用户指定且能导入 `funasr` 的 `ASR_PYTHON`，否则检查当前 `python3`。
- 本机没有可用环境但存在 `uv` 时，可以使用固定的 `funasr==1.3.22` 临时环境；首次依赖或模型下载前必须告知用户，并遵循平台授权流程。
- 缺少系统软件或依赖准备失败时停止，不自动安装系统软件，不产生终稿。

### 6.2 ASR 抽取

- 媒体时长来自 `ffprobe`，单位为秒。
- ASR、VAD 和标点模型使用固定 ModelScope ID；环境变量可显式覆盖模型位置或 ID。
- 优先复用本机完整缓存；没有缓存时才由 FunASR 解析固定 ID。
- 全文不能为空，句子列表不能为空。
- token 数必须与时间戳数完全一致；不得截断、补齐或猜测。
- 全文与句子内容在忽略空格、Unicode 标点和字母大小写后必须表达相同的发音序列；真实字词、数字和顺序差异仍须失败。
- 时间必须有限、非负、递增，且不得明显超过媒体时长。

### 6.3 大模型纠错

- 大模型读取全文以及当前模式所需的全部对齐单元。
- 输出只包含发生变化的稀疏范围；无错误时输出空 `changes`。
- 只纠正错字、同音词、专有名词、数字、英文和标点。
- 不确定时保留原文，不以“更通顺”为理由改写。
- 句子模式替换完整原句并保留该句原始起止时间。
- token 模式只能替换连续、合法且互不重叠的来源范围。
- 多 token 合并后的时间取来源范围首尾，不把时间平均分配给新字符。

### 6.4 合成与输出

最终格式以 `references/output-schema.md` 为唯一详细 schema 来源，并至少满足：

- `schema_version` 为 `1.0`，`language` 为 `zh-CN`。
- `source.name` 只包含文件名，不泄露本机绝对路径。
- `alignment.mode` 为 `sentence` 或 `token`。
- `units[].index` 从 0 连续编号。
- 每个单元满足 `0 <= start < end`，整体时间不倒退。
- `text` 严格等于所有 `units[].text` 顺序拼接。
- 输出使用原子写入；默认拒绝覆盖。
- 合成成功后必须再运行独立校验，只有两步都成功才可报告完成。

## 7. 失败与停止条件

以下情况必须停止，不得降级生成貌似可用的终稿：

- 输入文件或必要程序不存在。
- FunASR 不可导入、模型准备失败或没有返回有效结果。
- token 与时间戳数量不一致。
- 全文、句子或 token 不能通过内容一致性检查。
- 时间范围无效、重叠或越界。
- 纠错范围非法、重叠、为空或模式不匹配。
- 最终全文与对齐单元拼接不一致。
- 输出已经存在且用户没有传入 `--force`。

失败报告应指出停止阶段和可观察原因，不得把中间文件称为完成结果。

## 8. 验收标准

### 离线确定性验收

现有测试至少应持续证明：

- 中英文数字与后随标点可以无损还原原始文本。
- 全文与句子只有空格、标点数量或字母大小写差异时可以通过内容检查。
- token/时间戳数量不一致时失败。
- 全文与句子内容不一致时失败。
- 句子级稀疏纠错保留原时间。
- token 级连续范围可以合并且使用来源首尾时间。
- 空纠错清单保持原文不变。
- 重叠纠错范围被拒绝。
- 最终全文与对齐单元不一致时失败。
- 默认拒绝覆盖，显式 `--force` 才能替换。

### 真实媒体端到端验收

在声称 Skill 可实际交付前，至少用一段包含中文、英文缩写、数字和标点的本地媒体验证：

1. 句子模式完成抽取、纠错、合成和终检。
2. token 模式能对一个真实跨 token 错词进行纠正，且时间取原范围首尾。
3. 输出路径、模式、媒体总时长和单元数与交付说明一致。
4. 临时目录已清理，最终 JSON 不含原始 ASR 或纠错清单。
5. 对照音频抽查专有名词、数字及至少三个随机片段；保留未能确认的词并明确说明。

真实媒体测试可能触发依赖或模型下载，因此不属于无成本的离线结构验证，执行前需确认环境与授权。

## 9. 当前实现状态与证据强弱

### 已知事实

- 开发版已经包含 `SKILL.md`、UI 元数据、schema 参考、两个确定性脚本和离线测试。
- Skill 名称是 `asr-trans`，当前策略为仅显式调用。
- 开发版与当前发布目录的运行内容一致；发布目录存在 `.release`。
- 离线测试覆盖的关键不变量见 `scripts/test_asr_trans.py`。

### 合理推断

- 稀疏纠错清单比让大模型重写完整 JSON 更能降低漏句、错位和结构损坏风险。
- 固定模型 ID 并优先读缓存，可以降低模型短名解析和重复联网检查带来的漂移。
- 不保存原 ASR 能减小最终文件和敏感信息暴露面，但会牺牲事后审计能力。

### 尚缺信息或验证

- 尚无本文可引用的真实媒体端到端运行证据，不能仅凭离线单元测试确认 FunASR 当前环境可用。
- 尚未建立 ASR 与纠错质量指标，例如字错率、专有名词命中率或人工抽查基线。
- 对连字符、撇号、小数点等复杂英文/数字 token 的真实模型返回形态缺少样本验证。
- 长音视频的运行时间、内存占用、模型缓存体积和分批纠错上限尚未量化。
- 最终文件不含审计轨迹是已选择的边界；如未来需要可追溯性，应另行设计可选审计输出，而不是静默改变当前 schema。

## 10. 最值得关注的三个风险

1. **真实模型输出与本地 token 化假设不一致。** 离线 fixture 不能覆盖 FunASR 对复杂英文、数字和标点的全部返回形态；当前策略是检测到不一致立即停止。
2. **纠错正确但内容越权。** 大模型可能把口语整理误当识别纠错；稀疏变更和保守原则能降低风险，但仍需要真实样本抽查。
3. **可交付与可审计的取舍。** 最终 JSON 简洁且不泄露原始内容，但问题发生后无法仅凭终稿还原纠错依据。

## 11. 可能改变设计的关键问题

- 下游真正需要的是句子/token 定位，还是标准字幕格式（SRT/VTT）或词级置信度？
- 是否存在必须保留原 ASR 与纠错差异的审计场景？
- 真实材料是否包含多人对话、方言、嘈杂环境或大量中英混说？
- 可接受的首次模型下载体积、单次处理时长和最长媒体长度是多少？
- 纠错质量由谁、用什么样本和阈值验收？

在这些问题没有新答案前，当前第一版保持“中文口播、显式调用、保真纠错、两种对齐 JSON、失败即停止”的窄范围。
