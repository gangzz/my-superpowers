# 抖音媒体来源记录补充作品元数据

## 决定

- 延续现有 `*.mp4.source.json`，不把元数据写入 MP4 容器，也不另建第二份 JSON。
- 来源记录升级为 schema v2，在原有作品来源、文件校验、选择与传输摘要之外，保存 Manifest 中已确认的 `author`、`content` 和可选 `engagement`。
- 抖音作者保存稳定平台 ID、昵称和主页链接；作品只保存一个由作品 ID 构造的规范链接。
- 内容保存平台明确提供的标题、完整发布文案和话题标签。没有明确标题时省略，不能使用浏览器页面标题替代。
- 互动数据仅保存可靠取得的点赞、收藏、评论和分享计数，明确不定义播放量字段。
- 互动快照与下载同时产生，沿用顶层 `downloadedAt`，不新增 `collectedAt` 或 `capturedAt`。
- Extractor 版本、字段来源、缺失原因、选择依据和“是否对齐”不进入长期内容元数据。作品 ID 与目标对象不一致仍由 Extractor 直接失败。

## 原因

作品研究需要在媒体离开原目录后仍能识别作者和作品包装，但不需要把 Extractor 的调试过程复制到每个媒体附件。现有来源记录已经承担媒体与本地文件之间的稳定关联，扩展它比嵌入 MP4 标签或新增并行文件更清楚。

互动数会变化；当前只在下载时采一份，因此 `downloadedAt` 已足够说明快照时点。未来若支持不重新下载媒体而刷新互动数据，再单独设计多快照结构，不在第一版预留未使用字段。

## 验证边界

- 自动测试覆盖目标 `RENDER_DATA` 中作者、标题、完整文案、结构化标签和四类互动计数的提取，并验证 `play_count` 不进入 Manifest。
- sidecar 测试验证 schema v2 保存作品元数据、沿用 `downloadedAt`，且不泄露带签名媒体 URL。
- 本轮使用独立临时 Profile 和本机 Chrome 对真实样本页启动了可见浏览器核验，页面返回 `captcha`，因此没有取得真实作品元数据。没有绕过验证；安装前仍需用受管默认 Profile 在完成正常人工验证后，对一条公开作品做端到端检查。
