# 抖音入口、验证码判断与有限人工接管修复

决定：采用以下修复；用户已授权提交 GitHub、合并并安装本机版本。实际发布与安装结果分别以 Git 合并记录和本机 `.release` 为准。

## 原因与证据

- 原任务 `abf7c90b-9ed0-48d8-befb-17c54df927e2` 使用 `/video/7677380416872959247`，以 `captcha` 失败。旧实现只规范化短链，普通长链原样导航；人工接管也原样使用失败 URL。
- 使用同一 Profile、同一作品的精选页入口后，任务 `5d21c2f3-2cde-47f4-84fc-46033b421e80` 成功。证据支持入口处理不一致需要修复，但不能据此证明所有长链必然失败。
- 旧访问判断只要发现任意 captcha CSS 类／iframe，或正文含验证码相关词，就返回 captcha，没有验证可见性。原失败页未保留；后续使用同一 Profile、原始长链和未修改旧版复现相同错误：页面存在可播放视频元素，提取器未找到目标作品数据，正文无验证提示，仅有 display:none、0×0 的验证码 iframe。这次复现明确证实隐藏组件触发误报，不能把“页面能播放”等同于“目标数据已取到”。
- 上次 open_browser 命令成功后没有 close_browser，Host 保持 manualOpen，等待没有上限。用户报告没有得到完成／取消交互；命令权限审核记录为 allow，不能把人工窗口等待称为权限审批未完成。

## 修复

1. 标准作品长链、modal_id 链接、分享短链解析出 ID 后，下载和失败任务人工入口统一到精选作品页。sidecar 仍使用规范 `/video/<id>` 来源。
2. 验证组件须可见、位于视口内且有验证提示／滑块／画布／captcha iframe。忽略隐藏或透明组件、隐藏祖先、正文单独提及验证码；可见挑战优先于背景视频。仍严格校验目标身份和元数据。
3. open_browser 返回 requiresUserAction / manualTimeoutMs 并输出 manual_open；Skill 要求立即提供具体操作和完成／取消交互。新增 scripts/browser.mjs 供调用者提交打开或关闭命令。
4. 人工窗口关闭或默认10分钟超时后退出 Host，关闭 Context 并释放锁；保留未领取的 queued Job，不自动重试、不把超时当作用户同意。

## 验证与边界

- 全套49项测试通过，包含长链规范化、可见性判断、人工超时／关窗退出、保留排队任务和释放锁；超时与关窗状态机使用可控时钟及浏览器替身测试。
- 真实 Chrome 使用默认共享 Profile 对隐藏组件、透明祖先、display:none祖先、正文提及验证码、可见验证提示和可见captcha iframe六种页面验证通过。
- 修正版直接接收原始长链，实机任务 `fa14e8a7-5eb2-4cf8-b8f4-b5c574e1bf09` 成功：4,785,937字节、98.684807秒、720×1280、含音轨；SHA256为 `9f2d8591085f90b03cffc671d998083e21bb4b1b86524cd7faf5f1ed8d18fc78`，与已交付原件一致。未启动 NetworkProbe。
- 旧版复现后立即使用修正版对照，原始长链下载成功，文件大小和 SHA256 与此前交付一致；旧版失败与新版成功两次 Host 均释放锁。
- Skill结构验证及 git diff --check 通过，Host／专用Chrome退出、锁释放。超时是防止无限占用的保护设计，不替代用户交互；新增的是事件、控制脚本和 Skill 指令，没有新增图形按钮。未真实等待10分钟或让用户完成一轮验证码流程；不保证站点以后不触发验证。
