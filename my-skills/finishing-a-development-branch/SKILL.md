# 收尾开发分支

## 概述

**核心原则：** 验证测试 → 判断环境 → 呈现选项 → 执行选择。整合方式由用户决定，不由你替他决定。

**开始时说明：** “我正在使用 finishing-a-development-branch Skill 收尾这段工作。”

## 调用前提

- 用户显式调用本 Skill 时直接使用。
- 否则先说明当前工作已经完成到什么程度、收尾的预期收益和主要成本，获得用户明确同意后再开始。
- 用户在第 4 步菜单中选定的选项，即是对该选项所含动作的授权。菜单之外的动作——强制推送、删除远端分支、修改他人分支、向外部仓库提 PR——都需要用户单独明确要求。

## 第 1 步：验证测试

运行项目的完整测试套件（`npm test` / `cargo test` / `pytest` / `go test ./...`）。

**测试失败：** 报告失败内容并停下。菜单只在测试全绿之后出现：

```text
测试失败（<N> 个）。必须先修复才能收尾：

[展示失败内容]
```

**测试通过：** 继续第 2 步。

**项目没有可运行的测试命令：** 如实说明当前无法用测试验证这次改动，把是否继续收尾交给用户决定。不要把“没有测试”表述成“测试通过”。

## 第 2 步：判断环境

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 现在就记录路径——第 5 步会切换目录，之后汇报时还需要这个值
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

这决定呈现哪个菜单：

| 状态 | 菜单 |
|---|---|
| `GIT_DIR == GIT_COMMON`（普通仓库） | 标准 3 个选项 |
| `GIT_DIR != GIT_COMMON`，有具名分支（链接工作树） | 标准 3 个选项 |
| `GIT_DIR != GIT_COMMON`，分离 HEAD | 精简 2 个选项（没有本地合并） |

## 第 3 步：确定基线分支

基线分支就是这段工作分叉出来的那个分支——通常在计划、对话或分支的上游中已经写明。如果还不确定，就问：“这个分支是从 `<你的最佳猜测>` 分出来的吗？”合并前必须确认：合并进错误的基线，撤销代价很大。

## 第 4 步：呈现选项

**普通仓库和具名分支工作树——完整呈现这 3 个选项：**

```text
实施已完成。你希望怎么处理？

1. 在本地合并回 <base-branch>
2. 推送并创建 Pull Request
3. 保持分支现状（我稍后自己处理）

选哪个？
```

**分离 HEAD——完整呈现这 2 个选项：**

```text
实施已完成。当前处于分离 HEAD（工作区由外部环境管理）。

1. 推送为新分支并创建 Pull Request
2. 保持现状（我稍后自己处理）

选哪个？
```

菜单按上面的原文呈现，保持简洁，每个选项都来自上述列表。丢弃工作只在用户明确提出时才发生，见下方“用户要求丢弃工作时”。等待用户回答，整合决定属于用户。

## 第 5 步：执行选择

### 选项 1：本地合并

```bash
# 切到主仓库根目录：链接工作树中无法检出已被别处占用的分支
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 先合并，确认成功后再做任何删除
git checkout <base-branch>
git pull
git merge <feature-branch>

# 在合并结果上验证测试
<测试命令>
```

合并结果测试失败：停下，保留分支和工作树，开始排查。什么都还没有推送，这次合并是本地的、可恢复的。

合并结果全绿后，删除特性分支：

```bash
git branch -d <feature-branch>
```

然后按“工作树归属”一节汇报工作树位置。

### 选项 2：推送并创建 PR

```bash
git push -u origin <feature-branch>
# 从分离 HEAD 推送时，为远端分支命名：
# git push origin HEAD:refs/heads/<new-branch>
```

然后针对 `<base-branch>` 创建 PR：优先使用代码托管平台的 CLI，没有时使用推送后打印的创建链接；遵循仓库已有的 PR 模板和约定，并把 PR 地址报告给用户。

保留工作树——用户会在那里处理 PR 反馈。

### 选项 3：保持现状

汇报：“保留分支 `<name>`。工作树位于 `<path>`。”

### 用户要求丢弃工作时

这条路径只作为对“明确要求丢弃”的响应存在。先确认：

```text
这将永久删除：
- 分支 <name>
- 全部提交：<commit-list>

工作树 <path> 会保留，需要时请自行删除。

输入 'discard' 确认。
```

等待这个确切的确认词。收到后：

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
git branch -D <feature-branch>
```

## 工作树归属

**工作树由用户或运行环境创建和管理，不由本 Skill 删除。**

无论用户选择哪个选项，都不要执行 `git worktree remove`、`git worktree prune`，也不要删除工作树目录。收尾时只汇报：

```text
工作树保留在 <WORKTREE_PATH>，未做改动。
```

用户想清理时会自己处理，或明确要求你处理。

## 快速参考

| 选项 | 合并 | 推送 | 删除特性分支 | 工作树 |
|---|---|---|---|---|
| 1. 本地合并 | 是 | — | 是 | 保留并汇报位置 |
| 2. 创建 PR | — | 是 | — | 保留并汇报位置 |
| 3. 保持现状 | — | — | — | 保留并汇报位置 |
| 丢弃（仅在用户明确要求时） | — | — | 是（强制） | 保留并汇报位置 |

## 常见借口

| 借口 | 实际情况 |
|---|---|
| “这个会话前面测试通过过” | 在你即将整合的那棵树上跑一遍。一次绿色只能证明它当时跑过的那棵树。 |
| “他们显然是想合并” | 整合方式由用户决定。呈现菜单并等待。 |
| “这个功能看起来做完了，我顺便问问要不要丢弃” | 菜单就是完整的。丢弃只在用户用明确的话提出时才发生。 |
| “‘嗯，删了吧’算确认了” | 只有输入 `discard` 这个词才构成删除授权。 |
| “PR 建好了，工作树是多余的” | PR 反馈要在那个工作树里改。而且工作树不归你管，任何情况下都不要删。 |
| “合并结果的失败大概是偶发” | 合并结果失败就全部停下。分支和工作树原地不动，先排查。 |
| “基线分支显然是 main” | 确认分叉点或直接问。合并进错误的基线撤销代价很大。 |
| “推送被拒绝了，强推一下就好” | 推送被拒说明远端已经变化。先排查；强推只在用户明确要求时执行。 |
